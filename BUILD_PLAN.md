# BUILD_PLAN.md — Family Day Planner MVP

> Робочий документ для білду через Claude Code. Контракт продукту: PRODUCT_SPEC_v2.md.
> Стек: Next.js (App Router) на Vercel, GitHub. LLM через API (стартова модель — доступна;
> JSON-контракт однаковий незалежно від провайдера).
>
> Принцип порядку: від найризикованішого до найбезпечнішого. Кожен етап перевіряє ОДНЕ
> припущення. Валиться припущення — не йдемо далі, поки не полагодимо. Не будувати краї
> (реєстрація, бот, дизайн), поки не доведено, що ядро дає притомний результат.

---

## Загальні правила для Claude Code

- **Не забігати вперед.** Будуємо строго поетапно. Не додавати памʼять на етапі 1, не додавати Telegram на етапі 2. Кожна зайва фіча зараз краде час від перевірки ядра.
- **Solver — детермінований код, НЕ академічний constraint-solver.** Проста функція з циклами й перевірками. Ніяких зовнішніх solver-бібліотек, ніякої оптимізації. Мета — притомний день, не оптимальний.
- **LLM тільки парсить текст. LLM НЕ розкладає час.** Розкладку робить solver. Це не переговорюється — це головний архітектурний висновок ради.
- **JSON від LLM валідувати схемою, безпечно парсити.** Ніякої другої моделі для перевірки виводу.
- **Кожен крок — окремий commit** з осмисленим меседжем. Легше відкотитись.

## ЕТАП 1 — Довести aha-момент (найважливіший, робити першим)

**Припущення, яке перевіряємо:** коли вводиш реальний брудний день, solver дає притомний розклад, а не кашу.

**Що будуємо:** один екран, нуль бекенду-стану, нуль акаунтів. Ти єдиний користувач, дані ніде не зберігаються.

### 1.1 Скелет проєкту
- Next.js App Router, один route `/`
- API route `/api/plan` (сервер, щоб не світити LLM-ключ на клієнті)
- Змінна оточення для LLM-ключа
- Задеплоїти порожній скелет на Vercel одразу (перевірити, що пайплайн деплою працює, поки нема що ламати)

### 1.2 Контракт даних (визначити ДО коду, це найважливіше)

LLM-парсер приймає:
```
{ "text": "сирий текст мами", "today": "2026-09-05" }
```

LLM-парсер повертає (чистий JSON, нічого крім нього):
```
{
  "tasks": [
    { "title": "забрати старшого", "fixed_time": "15:00", "deadline": null },
    { "title": "тренування", "fixed_time": null, "deadline": null },
    { "title": "оплатити садок", "fixed_time": null, "deadline": "2026-09-08" }
  ]
}
```

Solver приймає: `tasks[]` + `rules` + `durations` (на етапі 1 durations = дефолти, rules = хардкод).
Solver повертає:
```
{
  "schedule": [
    { "title": "тренування", "start": "08:00", "duration_min": 60, "type": "flexible" },
    { "title": "забрати старшого", "start": "15:00", "duration_min": 30, "type": "fixed" }
  ],
  "overflow": [ { "title": "..." } ],
  "deadlines": [ { "title": "оплатити садок", "date": "2026-09-08" } ]
}
```

### 1.3 LLM-парсер (`/api/plan`, частина 1)
- Промпт: "розбери текст на справи, витягни фіксований час якщо є, витягни дедлайн-дату якщо є. Поверни ТІЛЬКИ JSON за схемою, без преамбули, без markdown."
- Few-shot: 2-3 приклади брудного вводу → чистий JSON (українською й російською, бо аудиторія двомовна)
- Валідувати вивід схемою. Якщо LLM повернув сміття — повторити раз, потім чесна помилка.

### 1.4 Solver (детермінований, серце етапу)
Порядок логіки:
1. Дефолтні тривалості: словник типових справ (тренування 60, вечеря 40, дорога 20...) + fallback 30 хв для незнайомих
2. Робочий день: хардкод вікна (напр. 07:00-22:00) — на етапі 1 без налаштувань
3. Хардкод правил для тесту: "тренування зранку", "зйомка після 17:00"
4. Постав фіксовані справи (fixed_time) на їхні місця
5. Розклади гнучкі справи у вільні вікна, поважаючи правила, додай буфери між справами
6. Що не влізло → `overflow[]` (НЕ стискати, НЕ викидати мовчки)
7. Дедлайни (deadline != null) → окремий блок `deadlines[]`, не в розкладі дня

### 1.5 Юніт-тести solver (писати одразу, це його перевага)
- порожній ввід → порожній розклад, не падає
- дві фіксовані справи на одну годину → обробка конфлікту (не мовчазне накладення)
- справ на 16 годин, вікон на 4 → overflow непорожній, решта розкладена
- справа з дедлайном → у deadlines, не в schedule
- незнайома справа → fallback-тривалість, не падає

### 1.6 Чорновий UI (навмисно потворний)
- textarea + кнопка "Розкласти"
- вивід розкладу вертикальним списком по годинах + окремо блок overflow + блок дедлайнів
- НУЛЬ дизайну. Системний шрифт, чорний текст, білий фон. Дизайн на етапі 5.

### ✅ Гейт етапу 1 (не проходити далі, поки не виконано)
Введи 5-7 РЕАЛЬНИХ своїх днів (брудних, як писала б мама). Питання: розклад притомний?
- Так, дає осмислений день → етап 2.
- Ні, каша (накладки, безглузді тривалості, ігнорує правила) → лагодити solver/промпт. НЕ будувати памʼять поверх зламаного ядра.

## ЕТАП 2 — Памʼять (твій рів)

**Припущення:** памʼять реально здешевлює ввід від дня до дня.

- Легкий ідентифікатор користувача (email або локальний профіль, БЕЗ Telegram поки)
- Зберігання між сесіями (проста БД: Vercel Postgres / SQLite / навіть KV — найпростіше що є)
- **Памʼять тривалостей:** мама поправила тривалість → зберегти → наступного разу ставити збережене
- **Памʼять рутини:** справи, що повторюються N днів → на день 2+ пропонувати як заготовку в textarea
- Правка тривалості в UI (просте поле/кнопки, НЕ drag-and-drop)
- Інвертована дія: тап "→ завтра" на справі; незакрите падає в завтрашній інбокс мовчки

### ✅ Гейт етапу 2
Введи свій день 7 разів поспіль. Міряй дві цифри щодня: скільки справ надрукував руками, скільки правок вніс.
- Обидві падають день 1 → день 7 → памʼять працює, етап 3.
- Стоять на місці → памʼять не знімає навантаження. Лагодити, поки не показав людям. Це головна метрика продукту.

## ЕТАП 3 — Доставка (замикає двотактний цикл)

**Припущення:** цикл живе без тебе за кермом.

- Telegram-бот: вечірній пінг "що на завтра?", ранкова видача плану
- Прив'язка Telegram до профілю (тепер ідентифікатор = Telegram tap)
- Email як запасний канал
- (бонус, якщо є час) голосове в бота → транскрипція → той самий текстовий пайплайн. НЕ окрема voice-фіча, просто інший вхід у наявний парсер.

### ✅ Гейт етапу 3
Проживи 3 дні на власному продукті через бота, без ручного запуску. Цикл замикається сам?

## ЕТАП 4 — Read-only шеринг (найдешевше, останнім)

**Припущення не перевіряє — просто закриває "family" рамку.**

- Share-посилання на статичний план (партнер відкриває в браузері)
- Або експорт картинкою в чат
- **ЖОРСТКА МЕЖА:** партнер тільки дивиться. Нуль акаунту, нуль кнопок, нуль sync, нуль "беру на себе". Будь-який інтерактив партнеру = вихід за скоуп v1.

---

## ЕТАП 5 — Дизайн (тільки коли ядро працює)

Аж тепер, коли логіка доведена, привести UI в порядок. Тоді читати frontend-design skill і робити свідомий візуальний вибір під аудиторію (перевантажена мама: спокій, ясність, нуль тривоги в кольорі й копірайті, узгоджено з retention-етикою зі спеку). До цього етапу — не витрачати на дизайн ані години.

---

## Паралельно всьому: concierge-трек (поза кодом)

Поки будуєш етапи 1-2, руками роби сервіс тим, хто платить наперед. Дає retention і WTP раніше за код. Може завернути тебе на етапі 2, якщо за реальну користь ніхто не платить — і це цінно дізнатись до, а не після білду.

---

## Що НЕ робити на жодному етапі до валідації

Multi-user, ролі, sync, інтерактив партнеру, автовитяг з календарів/пошти, нативний застосунок, web-push, drag-and-drop, друга модель для перевірки виводу, оптимізаційний solver. Усе це — out of scope v1 (див. PRODUCT_SPEC_v2 розділ 7).
